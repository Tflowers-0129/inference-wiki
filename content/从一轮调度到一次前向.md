# 从一轮调度到一次前向

上一章的第二轮安排了 `R1 D：1 + R2 D：1 + R3 P：4096 + R4 P：4094 = 8192` 个新 Token。调度器已经决定算哪些 Token，但设备还没有拿到可以直接执行的输入。

这中间还要回答三个问题：这些 Token 属于谁，应该看见哪些上下文，新算出的 KV 要写到哪里？沿着这一轮继续往下看，就能把调度、Attention 元数据、算子执行和性能分析连起来。

> 前半章的五 Token 算例以标准因果自注意力的稠密 Decoder 模型为背景，不加入投机、多模态、滑动窗口和分布式细节；后半章再讨论投机结果怎样影响 metadata，以及异步调度怎样连接两轮。字段名称借用常见实现帮助对照；布局、填充、排序与后端专用元数据因配置而异。构造例用于讲机制，没有给出设备实测耗时。

## 1. 调度结果怎样变成模型输入？

### 1.1 打包的是新 Token，历史留在 KV 中

完整第二轮有 8192 个新 Token，画起来太长。先缩成三条请求，数量变小，关系不变：

| 请求 | 工作 | 已有 KV 的 Token 数 | 本轮新计算数 | 本轮位置，按 0 起算 |
| --- | --- | --- | --- | --- |
| A | Decode | 8 | 1 | 8 |
| B | Decode | 5 | 1 | 5 |
| C | 分块 Prefill | 2 | 3 | 2、3、4 |

下面选择 A、B、C 的打包顺序，把本轮输入展平成五行。C 是已经计算过前一块的 Prefill，所以其位置从 2 接着走；A、B 的输入则是各自上一轮采样得到、尚未计算 KV 的 Token。

```text
input_ids        = [ a8, b5, c2, c3, c4 ]
positions        = [  8,  5,  2,  3,  4 ]
query_start_loc  = [ 0, 1, 2, 5 ]
seq_lens         = [ 9, 6, 5 ]
```

`a8` 等是 Token 的符号名，不是实际词表 ID。`positions` 表示请求内的位置，不是这五行在批次中的行号。

`query_start_loc` 用累加边界把五行重新分成 `[0,1)`、`[1,2)`、`[2,5)` 三段，差分得到本轮 query 长度 `[1,1,3]`。本例 `seq_lens` 表示包含本轮新 Token 的总长度：`已有长度 + query 长度`。这与三条请求的最终输出长度没有关系。[输入准备设计](https://docs.vllm.ai/projects/ascend/en/main/developer_guide/Design_Documents/ModelRunner_prepare_inputs.html)、[Attention 元数据定义](https://docs.vllm.ai/en/latest/api/vllm/v1/attention/backend/)

![本轮五个 Token 的打包、请求边界与 KV 地址](../dist/assets/batch-metadata.svg)

### 1.2 拼在一起，不代表彼此可以看见

A 不能注意到 B、C。C 本轮第一个位置 2，只能看见自己的位置 0～2；位置 4 才能看见自己的 0～4。打包只改变存储与计算的组织方式，请求边界和因果关系仍要保持。

Runner 会据调度结果准备输入与通用信息，再由 Attention 后端组织其需要的描述。有的后端还会生成切分、工作区或图回放相关数据。**metadata 是“怎样执行这次 Attention”的描述；它既不是 KV 内容，也不能代替模型前向。**

## 2. 这五行进入一层模型后发生什么？

先忽略实现中的融合，把一个普通 Transformer 层拆开：

1. 当前隐藏状态经过归一化、QKV 投影等计算，得到本轮新 Token 的 Q、K、V；位置编码按模型设计参与其中。
2. 新 K、V 写入各请求的缓存位置。Attention 用当前 Q 读取该请求允许访问的历史与当前 K、V。
3. Attention 输出经过输出投影，再进入残差、归一化和 MLP 等计算，形成下一层输入。

这只是数据依赖图。实际 Kernel 可能融合、拆分或交错执行，不能用上面的三个步骤去数设备上的三个算子。

![线性层共享权重，Attention 按请求访问 KV](../dist/assets/forward-dataflow.svg)

线性层可以把五行组织成同一次矩阵乘法，因为它们使用同一套层权重。Attention 则必须知道行与请求的关系。P 与 D 可能共用部分执行路径，也可能进入不同 Kernel；“混合批次”不保证每个算子都只有一次调用。

还有一个常见误解：**Decode 会读取历史 KV，但不会为整段历史重新运行所有层的 QKV 投影和 MLP。** 当前轮只为新输入位置推进这些计算，已经缓存的历史 KV 被继续使用。最后，完成 Prefill 的请求或 Decode 请求按需要选取隐藏状态，经过输出头、采样等路径得到下一批输出；未完成的 Prefill chunk 不因此变成客户端输出。

## 3. 只有 200 个新 Token，设备为什么还可能很忙？

mbt 数的是本轮新计算位置，没数模型权重有多大，也没数每个 Q 需要访问多长的 KV。

### 3.1 权重怎样被一批 Token 复用？

对一个线性层写成 `Y = XW`，令 `X` 为 `[T,H]`，`W` 为 `[H,F]`。按一次乘加计两次浮点运算，其主要计算量约为：

```text
计算量 C ≈ 2 × T × H × F
理想数据量 M ≈ s × (T×H + H×F + T×F)
```

这里 `s` 是每元素字节数；理想数据量假设每个输入、权重各读一次，输出写一次，忽略偏置、量化、工作区和中间结果。增大 `T` 后，同一份权重可以服务更多输入行，权重读取被更多计算摊薄。这解释了批处理为何可能提高效率，**不保证耗时按 T 线性增长，也不保证批次越大越好**。矩阵形状、切块、片上容量与并行度都会影响真正的数据搬运。[矩阵乘法的计算与访存分析](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html)

### 3.2 上下文增长，KV 访问也增长

对标准全 Attention，普通 Decode 每条序列只有一个新 Q，仍要对该请求允许访问的 K、V 做 Attention。若第 i 条请求的有效上下文长度为 `S_i`，可用下式估计这一轮跨层相关的 KV 逻辑数据规模：

```text
V_KV ≈ 2 × L × Hkv × dh × sKV × Σ S_i
```

`L` 为层数，`Hkv` 为 KV 头数，`dh` 为头维度，2 表示 K 与 V。它描述数据规模，**不等于实际 HBM 读字节数**；缓存复用、共享前缀、Kernel 切分、并行分片和数据格式都会改变流量。滑动窗口、压缩或其他 Attention 结构还会改变公式前提。

所以，同为 200 条 D，2K 与 32K 上下文的工作不能只用“都是 200 Token”比较。对 Prefill chunk，本轮多个 Q 又会访问不同长度的因果前缀，计算与复用方式也发生变化。

### 3.3 用 Roofline 提问，不给 P、D 永久贴标签

把算术强度记作 `I = C/M`。在计算与搬运有足够并行度的简化模型里，性能上界为 `min(P, B×I)`，相应时间下界可写作 `max(C/P, M/B)`；`P`、`B` 分别是所选精度与内存层级的算力和带宽能力。

这能帮助判断该先研究计算还是数据搬运，却不是整轮时延预测器。小批次可能并行度不足；图提交、同步、通信等也没有放进公式。更不能把芯片标称峰值当成程序已经达到的性能。比较时还要统一 FLOP 计数、精度与流量口径。[性能约束分析](https://docs.nvidia.com/deeplearning/performance/dl-performance-gpu-background/)

“P 常偏计算，D 常偏访存”可以用作最初假设。批量、上下文、量化和 Kernel 一变，就应重新检查，不能靠阶段名称判定瓶颈。

## 4. 连续上下文怎样找到分散的 KV？

沿用五 Token 例子，额外假设每块容纳 4 个 Token。请求看到的是逻辑位置，块表把逻辑块编号映射到 KV 池里的物理块：

```text
A 的块表 = [7, 2, 9]     B 的块表 = [5, 6]     C 的块表 = [8, 3]
逻辑块号 = floor(position / 4)
块内偏移 = position % 4
槽号     = 物理块号 × 4 + 块内偏移
```

A 的历史位置 0～7 已占两个逻辑块，本轮位置 8 需要逻辑块 2，示例中新分配物理块 9，槽号是 36。C 的位置 2、3、4 分别落在槽 34、35、12。因此，本轮写入对应的 `slot_mapping = [36,25,34,35,12]`。

**块表帮助 Attention 找到上下文的 KV；slot mapping 指出本轮新 KV 写到哪里。** 这里槽号是扁平化教学编号，实际张量还具有层、K/V、头与维度等布局。块表也可能属于不同 KV 组，不能把这个四则运算当成所有后端的地址公式。[PagedAttention 设计](https://docs.vllm.ai/en/latest/design/paged_attention/)

![逻辑位置经块表访问物理 KV，匹配前缀可共享已有块](../dist/assets/kv-addressing.svg)

符合复用条件的请求可以让块表指向同一批已计算的前缀块。命中还取决于完整前缀和必要的模型、适配器等身份信息，不能见到一小段相同文本就共享。引用释放与缓存淘汰则沿用上一章的区分：请求不用了，不必立即擦除 KV。[前缀缓存设计](https://docs.vllm.ai/en/latest/design/prefix_caching/)

PagedAttention 解决块化 KV 的访问与管理；FlashAttention 研究 Attention 内部怎样通过分块、片上复用等方式减少 HBM 与片上存储间的数据搬运。二者回答的问题不同，可以组合使用。FlashAttention 保持精确 Attention 的语义，也不能被解释成“少看一些历史 Token”。[FlashAttention 论文](https://arxiv.org/abs/2205.14135)

## 5. metadata 为什么会截断提交流水？

metadata 的计算量常常不大，关键在于数据从哪里来、谁必须读取它。前面五 Token 例子的调度数、请求顺序和已分配块表，CPU 已经知道，在 CPU 上构造它们不天然需要等待设备。投机验证的接受数、拒绝数与修正后的有效长度，却要等设备算出结果。下一轮 Python 若立刻要读精确值，依赖就变成：

```text
设备完成验证 → D2H 回读 → CPU 等待并修正 metadata → H2D → 下一轮前向
```

传回的可能只有几个整数，代价却不只是搬这几个字节。Host 必须等结果产生，才能继续提交后续工作；设备又没有其他可执行任务时，等待才暴露成空泡。Ascend 的 `_update_seq_lens_cpu()` 就包含等待 D2H event 后消费精确计数的路径，`_can_skip_spec_cpu_length_sync()` 则按配置与后端能力判断能否省去回读。[长度更新与跳过条件](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/worker/v2/model_runner.py)

![metadata 的 Host 往返、设备侧构造与真正消费时的等待](../dist/assets/metadata-pipeline.svg)

### 5.1 Triton 融合算子分别省掉什么？

设备上常见的派生计算包括差分、索引、取模、`where`、填充等。分开写可以产生许多小 Kernel；融合让中间值留在设备，减少 launch 与中间读写。vLLM Ascend 中可以沿下面四处对照：

| 实现 | 做什么 | 省在哪里 |
| --- | --- | --- |
| `_compute_slot_mapping_kernel` | 用 positions、请求边界和块表计算写入槽，处理 padding | 把地址推导留在设备，合并多步张量操作。[源码](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/ops/triton/compute_slot_mapping.py) |
| `compute_slot_mapping_fused_groups` | 支持条件满足时，一次 launch 处理多个 KV cache group | 减少逐组提交。[调用处](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/worker/block_table.py) |
| `prepare_inputs_padded_kernel` | 从有效输出计数推导拒绝数与后续采样索引 | 在设备上融合派生值计算。[源码](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/ops/triton/spec_decode/utils.py) |
| `_prepare_dflash_inputs_kernel` | 在特定投机路径准备 positions、slot mapping、采样映射与 padding | 融合更大范围的输入准备。[源码](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/ops/triton/v2/spec_decode/prepare_dflash_inputs.py) |

`prepare_inputs_padded` 的思路尤其值得留意：不立即按接受数压紧全部输入，保留拒绝位置作 padding，再按索引筛选。**容量、有效范围与采样位置分开描述，可以减少为动态形状回到 Host 的需求。** 这只适用于相应实现约定；下游必须正确处理 padding，容量上界不能冒充真实有效长度。[输入准备逻辑](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/worker/v1/spec_decode/llm_base_proposer.py)

CPU 镜像也要问“它是否仍然精确”。普通路径可维护准确计数；投机结果未回收时，Host 的长度可能只是乐观上界，设备上的拒绝修正状态才是权威。需要精确 Host 长度的消费者仍要等待，直接删除同步会读到旧值。

### 5.2 空白不全是同一种原因

融合不自动消除同步：下游若把设备张量 `.tolist()` 成 Python list，仍会触发回读；CPU 张量的同名操作则没有这次设备等待。Ascend 的 Attention builder 会根据路径选择长度来源，再构造 Python 长度列表。[长度来源](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/attention/utils.py)、[metadata builder](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/attention/attention_v1.py) 重复 copy 可能增加流量和排队，小 Kernel 可能使提交跟不上设备，二者也都不能仅凭函数名叫“同步”。

`DeviceMetadataExecutor` 在独立 NPU 流上生产 metadata，按阶段和 KV group 记录就绪事件，消费者到使用处再等待。**设备流等待 event 保留数据依赖，通常不要求 Host 在该处停住；其他独立工作有机会重叠。** 但消费者尚未就绪时仍会等，缓冲区复用也必须有保护。[设备侧执行器](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/worker/device_metadata.py)

图回放同样主要减少满足条件的执行序列的重复提交开销，QKV、Attention、MLP 与 KV 访问仍要执行；图内外的 metadata 依赖也仍然成立。[图执行设计](https://docs.vllm.ai/en/latest/design/cuda_graphs/)

看 Trace 时先对齐**结果产生、D2H 完成、CPU 继续提交、下一次 Kernel／图开始**四个时刻。Host 卡在等待调用，查结果往返；Host 一直忙于 packing 和提交，查小 Kernel、重复复制与 Python 工作量。还要接上发送、接收时刻才解释得了 ITL。Python 调用提前返回不代表设备执行结束；采集和计时本身也可能扰动时间线。

## 6. 异步调度发生在两轮之间

同步推进时，第 n 轮提交后，CPU 收回输出、更新请求状态，再安排第 n+1 轮。异步调度让第 n 轮尚在设备执行、采样或回传时，CPU 提前安排后续工作，把调度、准备、执行和回收接成流水。短 Decode step 中 Host 开销比例更容易显露，因此尤其值得观察；机制并不只服务于 Decode。

![同步逐轮等待与异步提前调度的 CPU、设备及输出时间线](../dist/assets/async-scheduling.svg)

### 6.1 Token 还没回 CPU，下一轮怎么排？

调度器可以先决定预算与占位，Worker 再接上设备端的真实输入。`AsyncScheduler` 用 `num_output_placeholders` 等状态记录尚未回收的输出，真实结果回来后消解或修正；Worker 保留 `prev_sampled_token_ids`，在后续输入准备中接续真实 Token。**占位用于调度记账，不能作为词表 ID 送进模型。** 下一轮 Attention 仍需等待其真实输入及 KV 就绪，自回归依赖没有被跳过。[占位记账](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/async_scheduler.py)、[设备端输入接续](https://github.com/vllm-project/vllm/blob/main/vllm/v1/worker/gpu_model_runner.py)

读 `num_computed_tokens` 也要看它属于哪一侧：Scheduler 会在安排后提前推进该计数，不能据此认定设备已经算完。投机路径还要按设备上的有效输出数修正真实进度、positions 与 seq_lens，Host 再随结果回收修正记账。[调度后的状态推进](https://github.com/vllm-project/vllm/blob/main/vllm/v1/core/sched/scheduler.py)

输出也没有消失：D2H、停止判断、请求更新和发送仍需完成。异步输出包装与后台回收线程使等待尽量不挡住持续提交。队列容量、语法约束、停止与取消等条件仍会限制能提前推进多少工作。[后台输出处理](https://github.com/vllm-project/vllm/blob/main/vllm/v1/executor/multiproc_executor.py)

### 6.2 在 Ascend 中沿什么顺序读？

入口跨了上游引擎与 Ascend Worker。Ascend 的一条 `NPUModelRunner` 路径继承上游 `GPUModelRunner`，只搜 Ascend 仓库会漏掉父类行为；其他 Runner 路径还需分别核对。[继承与 Ascend 采样处理](https://github.com/vllm-project/vllm-ascend/blob/main/vllm_ascend/worker/v1/model_runner.py)

1. 从 `async_scheduling` 与 `get_scheduler_cls()` 确认实际选择的 Scheduler，再看 executor 的能力与队列配置。[Scheduler 选择](https://github.com/vllm-project/vllm/blob/main/vllm/config/scheduler.py)、[在途批次数配置](https://github.com/vllm-project/vllm/blob/main/vllm/config/vllm.py)
2. 看 `EngineCore.step_with_batch_queue()`：有空间时先安排、提交，把 future 入队；到需要回收时才等最早结果并更新调度器。[引擎循环](https://github.com/vllm-project/vllm/blob/main/vllm/v1/engine/core.py)
3. 跟踪 `num_output_placeholders`、输入接续和输出回收，确认尚未完成的一轮如何被记账、修正。

把队列路径压缩成下面的阅读顺序，更容易找到跨轮重叠发生的位置。这是省略条件分支的伪代码，不是可以直接执行的接口示例：

```text
schedule() → execute_model(non_block=True) → sample_tokens(non_block=True)
           → 将 future 与本轮 scheduler_output 入队
           → 队列尚有空间：先返回，继续后续调度

需要回收时：取最早提交的一批 → future.result() → update_from_output()
```

`non_block=True` 只说明调用可以提前返回；如果紧接着 `future.result()`，并未形成跨轮重叠。batch queue 也用于流水线并行，看到队列本身不足以证明异步调度已开启。要在实际配置和 Trace 中确认：**结果 n 回收前，是否已进行后续调度，Worker 是否还能持续提交。**

这与上一节直接相连：CPU 即使提前排好下一轮，Worker 若准备 metadata 时仍等待上一轮接受数回到 Host，流水还会在这里停住。投机解码又让 query 长度、有效 KV 与一次输出 Token 数发生变化，具体边界接着读[《投机解码：调度、元数据与流式时延》](投机解码与流式指标.md)。异步调度、算子融合和图回放分别减少不同的暴露开销，不能只开一个开关就假定所有等待都已隐藏。

## 7. 回到 PD：RP、RD 为什么不能当常数？

前一章用 P、D 的服务能力讨论配比。现在可以继续拆：P 的批量和 chunk 影响矩阵形状；D 的批量和上下文影响权重复用与 KV 工作量。输入、输出长度和缓存命中变化，测得的 RP、RD 就可能变化。把某次 tokens/s 原封不动带进另一组负载，配比就失去了依据。

多卡还会引入张量并行中的集合通信、流水线阶段传递，某些模型也涉及专家间数据交换。PD 则多出跨实例 KV 搬运、目标缓存准备和交接等待。通信、拷贝能否与计算重叠，要看数据依赖、链路和实现；看到异步接口不代表传输已经被隐藏。

这些因素值得各自展开，但本章先保留一个检查顺序：**先确认工作量和输入，再量计算与搬运，最后判断是否存在可以重叠的独立工作。**

## 8. 下一次实测，可以只改一个变量

| 实验 | 保持什么 | 改变什么 | 重点观察 |
| --- | --- | --- | --- |
| D 批量 | 模型、上下文分布、输出与执行模式 | 每轮 D 请求数 | 矩阵形状、设备时间、吞吐与单请求间隔 |
| 上下文 | D 请求数和执行模式 | 有效上下文长度 | Attention 时间、KV 容量与访存计数 |
| 混部 | D 群体与到达方式 | P chunk 和加入时点 | 混合轮组成、D 输出时间轴 |
| 图执行 | 尽量匹配输入与实际批次 | 支持的执行模式 | CPU 提交、设备空洞、padding 与总时延 |
| metadata 路径 | 请求与接受数分布、后端和输入布局 | 支持的融合或设备侧准备路径 | D2H 等待、Kernel 数、重复 copy、消费者就绪时点 |
| 异步调度 | 模型、负载、执行与采样条件 | 支持的同步／异步调度配置 | 后续 schedule 与结果回收的先后、队列深度、Host 与设备重叠、ITL 分布 |

记录真实调度数、请求边界、query 长度、有效上下文和执行路径，先核实比较对象是否一致。闭环并发下服务变慢还会降低请求补入速率，不能把“并发没变”当成负载工作量完全相同。

本章构造例可以检查字段与地址是否一致；它不能给出哪一款设备应有多少毫秒。需要保留的是这条排查路径：调度数解释输入，metadata 解释边界与地址，算子解释工作量，Trace 再解释时间。
